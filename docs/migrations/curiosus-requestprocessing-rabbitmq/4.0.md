Requires `net9.0` or `net10.0`. Coming from `Curiosity.*` 1.x? Start with the [overview](../index.md).

`Curiosus.RequestProcessing.RabbitMQ` 4.0 belongs to milestone M5, which reworks request processing and RabbitMQ
([#77](https://github.com/curiosus-dev/Curiosus.Utils/issues/77)); this page grows with each change of the release.
Read the [Curiosus.RequestProcessing 3.0](../curiosus-requestprocessing/3.0.md) page too.

## Breaking changes

- [Options](#options) ([#44](https://github.com/curiosus-dev/Curiosus.Utils/issues/44))

## Options

The options validated themselves with the options model of `Curiosus.Configuration` (`IValidatableOptions`,
`AssertValid()`), which is deprecated. They are plain classes on `Microsoft.Extensions.Options` now, validated with
data annotations when the host starts, and the `IRabbitMQRequestProcessorNodeOptions` interface is replaced with the
`RabbitMQRequestProcessorNodeOptions` class.

| Before | Now |
|---|---|
| `IRabbitMQRequestProcessorNodeOptions` implemented by your `RequestProcessorNodeOptions` subclass | derive from `RabbitMQRequestProcessorNodeOptions` |
| `AddRabbitMQRequestProcessor<...>(nodeOptions)` with an instance | `AddRabbitMQRequestProcessor<...>()` returns `OptionsBuilder<TOptions>`; bind with `.BindConfiguration("RequestProcessor")` |
| `AssertValid()` in `AddRabbitMQRequestProcessor` and the `RabbitMQEventReceiver` constructor | `OptionsValidationException` when the host starts |
| `RabbitMQEventReceiverOptions.Validate(prefix)` | `[Required]`, `[Range]` attributes with the same rules |
| `Port` above 65535 allowed | `Port` is 1..65535 |

Before:

```csharp
public class MyNodeOptions : RequestProcessorNodeOptions, IRabbitMQRequestProcessorNodeOptions
{
    public RabbitMQEventReceiverOptions RabbitMQEventReceiver { get; } = new();

    public override IReadOnlyCollection<ConfigurationValidationError> Validate(string? prefix = null)
    {
        var errors = new ConfigurationValidationErrorCollection(prefix);
        errors.AddErrors(base.Validate(prefix));
        errors.AddErrors(RabbitMQEventReceiver.Validate(nameof(RabbitMQEventReceiver)));
        return errors;
    }
}

var configuration = builder.Configuration.Get<AppConfiguration>()!;
configuration.AssertValid();
builder.Services.AddRabbitMQRequestProcessor<
    MyRequest, MyWorker, WorkerBasicExtraParams, MyBootstrapper, MyNodeOptions, MyDispatcher, MyProcessingInfo>(
    configuration.RequestProcessor);
```

After:

```csharp
public class MyNodeOptions : RabbitMQRequestProcessorNodeOptions
{
}

builder.Services
    .AddRabbitMQRequestProcessor<
        MyRequest, MyWorker, WorkerBasicExtraParams, MyBootstrapper, MyNodeOptions, MyDispatcher, MyProcessingInfo>()
    .BindConfiguration("RequestProcessor");
```

The configuration keeps its shape (`RequestProcessor:RabbitMQEventReceiver:QueueName`, ...).
`RabbitMQEventReceiver` is validated with the node options (`[ValidateObjectMembers]`); validation errors name the
options, never their values. Rules over several properties of your subclass go to your own
`IValidateOptions<MyNodeOptions>`, and the options of a subclass of a subclass are validated as described on the
[Curiosus.RequestProcessing 3.0](../curiosus-requestprocessing/3.0.md#subclasses-of-the-options) page.

Checklist:

- [ ] Derive the node options from `RabbitMQRequestProcessorNodeOptions` and remove
  `IRabbitMQRequestProcessorNodeOptions` and the `RabbitMQEventReceiver` property you declared.
- [ ] Replace `AddRabbitMQRequestProcessor<...>(instance)` with `.BindConfiguration("...")` on its result, remove
  `AssertValid()` calls.
- [ ] Move the `Validate(prefix)` override to attributes and an `IValidateOptions<T>`.
- [ ] Change the constraint `RequestProcessorNodeOptions, IRabbitMQRequestProcessorNodeOptions` to
  `RabbitMQRequestProcessorNodeOptions` if you repeat it in your own generic types.
