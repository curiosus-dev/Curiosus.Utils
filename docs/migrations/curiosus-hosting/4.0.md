Requires `net9.0` or `net10.0`. Coming from `Curiosity.*` 1.x? Start with the [overview](../index.md).

`Curiosus.Hosting` 4.0 replaces the bootstrappers with extension methods on `IHostApplicationBuilder`. This page grows
with each change of the release ([#41](https://github.com/curiosus-dev/Curiosus.Utils/issues/41),
[#43](https://github.com/curiosus-dev/Curiosus.Utils/issues/43)–[#46](https://github.com/curiosus-dev/Curiosus.Utils/issues/46)).

## Bootstrappers → Program.cs

The bootstrappers were a class hierarchy around the .NET Core 2.x host: each `ConfigureServices` overload kept one
delegate (a second call replaced the first), the tool bootstrapper never disposed its service provider, the
configuration was loaded twice and `host.InitAsync()` had to be called by hand. 4.0 builds on
`Host.CreateApplicationBuilder`: a top-level `Program.cs` with `CuriosusHost.CreateBuilder(args).AddCuriosusDefaults()`
and `CuriosusApp.RunAsync`.

Removed: `CuriosusAppBootstrapper`, `CuriosusServiceAppBootstrapper`, `CuriosusToolAppBootstrapper` (all three),
`CuriosusCLIArguments`, `ICuriosusAppConfiguration`, `CuriosusAppConfiguration`, `CuriosusAppConfigurationValidator`,
`AddAppInitialization`, `HostExtensions.InitAsync`, `AddPerformanceMeasures`, the public `FireAndForgetInitializer` and
the non-generic `ILogger` named `main`. The package no longer depends on `EntryPoint` and
`System.ComponentModel.Annotations`.

Service, before:

```csharp
public class AppBootstrapper : CuriosusServiceAppBootstrapper<CuriosusCLIArguments, AppConfiguration>
{
    public AppBootstrapper()
    {
        ConfigureServices((context, services, configuration) =>
        {
            services.AddSmtpEMailSender(configuration.Smtp);
            services.AddHostedService<Worker>();
        });
    }
}

return await new AppBootstrapper().RunAsync(args);
```

After:

```csharp
var builder = CuriosusHost.CreateBuilder(args).AddCuriosusDefaults();
builder.AddCuriosusNLog();
builder.Services.AddCuriosusOptions<SmtpOptions>("Smtp");
builder.Services.AddHostedService<Worker>();

return await CuriosusApp.RunAsync(builder.Build());
```

Tool, before: a `CuriosusToolAppBootstrapper` with `ExecuteAsync(serviceProvider, rawArguments, arguments,
configuration, cancellationToken)`, or a `BackgroundService` that does the work and calls `StopApplication()` (always
exit code 0). After: the work is a command, its result is the exit code:

```csharp
var builder = CuriosusHost.CreateBuilder(args).AddCuriosusDefaults();
builder.Services.AddSingleton<Importer>();

return await CuriosusApp.RunAsync(builder.Build(), (services, cancellationToken) =>
    services.GetRequiredService<Importer>().RunAsync(cancellationToken));   // Task<int>
```

The host starts first (initializers and hosted services), the command runs in a DI scope with a token that is
cancelled on Ctrl+C / SIGTERM, then the host stops and is disposed.

Web apps: `CuriosusWebHost.CreateBuilder(args)` of `Curiosus.Hosting.Web`, see its
[4.0 migration notes](../curiosus-hosting-web/4.0.md) for `Startup` → `Program.cs`.

Non-generic `ILogger` injected in app classes → `ILogger<T>` of the class.

## Command line arguments

`CuriosusCLIArguments` and EntryPoint are gone. What the bootstrappers offered keeps working without code:
`-c` / `--config` (a directory, or now a single file) and `-v` / `--version` (prints `App version: x.y.z.w` and exits
with 0 right in `CreateBuilder`, before configuration is read); every other `--Key value` argument overrides
configuration as before. Typed options and subcommands come from
[System.CommandLine](https://learn.microsoft.com/dotnet/standard/commandline/) 2.x: parse first, build the host in the
action, register what the app needs:

```csharp
var phoneOption = new Option<string>("--phone", "-p") { Required = true };
var configOption = new Option<string?>("--config", "-c");   // so System.CommandLine accepts it
var rootCommand = new RootCommand("Sends a test SMS") { phoneOption, configOption };

rootCommand.SetAction(async (parseResult, cancellationToken) =>
{
    var builder = CuriosusHost.CreateBuilder(args).AddCuriosusDefaults();
    builder.Services.AddSingleton(new SendOptions(parseResult.GetValue(phoneOption)!));
    return await CuriosusApp.RunAsync(builder.Build(), RunAsync, cancellationToken);
});

return await rootCommand.Parse(args).InvokeAsync();
```

System.CommandLine handles `--help` and `--version` itself before the action runs. Pass `args` to `CreateBuilder` only
if every option takes a value: the configuration provider reads the token after a switch as its value, so a boolean
flag such as `--dry-run` would swallow the next argument; with flags, pass the configuration arguments only. A custom `--windows` flag that registered
`WindowsServiceLifetime` is not needed: `AddCuriosusDefaults` registers the Windows service and systemd lifetimes,
which do nothing outside a service.

## Configuration class → options per section

The root configuration class (`AppName`, `Culture`, `Log` plus the app's sections) bound the whole configuration into
one object that was injected everywhere. Bind each section to its own options class with `AddCuriosusOptions<T>` of
Curiosus.Configuration and inject `IOptions<T>`; validation runs when the host starts and an invalid section makes
`RunAsync` return `InvalidOptions` (1). See the [Curiosus.Configuration 3.0 notes](../curiosus-configuration/3.0.md).

Short-term recipe for a large app: bind the old class once and register it (and the interfaces it implements):

```csharp
var configuration = builder.Configuration.Get<AppConfiguration>() ?? new AppConfiguration();
configuration.AssertValid();
builder.Services.AddSingleton(configuration);
builder.Services.AddSingleton<IOrderSettings>(configuration);
```

`TransformConfiguration` (copying shared credentials into nested options, derived values) → `PostConfigure<T>`, which
runs before validation:

```csharp
builder.Services.AddCuriosusOptions<ImportOptions>("Import");
builder.Services.PostConfigure<ImportOptions>(o => o.Smtp.Password ??= builder.Configuration["SharedSmtp:Password"]);
```

`AppName` stays a top-level key: it names the app in the start/stop messages and NLog's `${var:appname}`
(default: the assembly name).

## Environment, content root and configuration files

- Environment: `DOTNET_ENVIRONMENT`, then `ASPNETCORE_ENVIRONMENT`, then `Production` (was `ASPNETCORE_ENVIRONMENT` only,
  `null` when unset). Workers may set `DOTNET_ENVIRONMENT`; existing `ASPNETCORE_ENVIRONMENT` keeps working.
- Content root: the current directory, or the binaries directory when the app runs as a systemd unit or a Windows
  service. Relative paths in configuration (`Log`, temp directories) resolve against it.
- Files: `config.yml`, `config.secret.yml`, `config.{Environment}.yml` (+ `.secret`) and, outside `Production`,
  `config.{Environment}.{UserName}.yml` (+ `.secret`). The environment file is now loaded in `Production` too; the
  personal file uses `Environment.UserName` instead of the `USER` variable. User secrets, environment variables and
  command line arguments override the files, as before.
- `-c` takes a directory as before, or a single file that is loaded alone.

## App initializers, culture and exit codes

- `IAppInitializer`s run automatically before hosted services start (`IHostedLifecycleService.StartingAsync`), in
  registration order: drop `AddAppInitialization()` and `host.InitAsync()`. An initializer that needed
  `IServiceCollection` (for example to run migrations on a service registered later) gets what it needs from its
  constructor. Hosted services are constructed before that (`InitAsync()` ran before the host was built): a constructor
  must not rely on the culture, `UniqueIdGenerator` or an initializer.
- `Culture:DefaultCulture` is applied process-wide (culture and UI culture) when it is set; without it the culture of
  the system stays (the bootstrappers forced `en-US`). Set it in `config.yml` if views rely on it.
- `UniqueId:GeneratorId` initializes `UniqueIdGenerator` (the bootstrappers never did).
- `CuriosusExitCodes` are constants: `Success` (0), `InvalidOptions` (1, was `IncorrectConfiguration`),
  `UnhandledException` (2, also when a `BackgroundService` fails and stops the host, so `Restart=on-failure` of
  systemd restarts it), `Cancellation` (3); a tool returns its command's code. When the command fails, the host is
  still stopped, so `{AppName} is stopped` is written.
- `PerformanceMeasurer` is registered by `AddCuriosusDefaults` (was `AddPerformanceMeasures()`).

Checklist:

- [ ] Replace the bootstrapper with a top-level `Program.cs` (`CuriosusHost.CreateBuilder(args).AddCuriosusDefaults()`,
  `CuriosusApp.RunAsync`); tools return their exit code from the command.
- [ ] Move typed CLI arguments to System.CommandLine; keep `-c` accepted.
- [ ] Bind sections with `AddCuriosusOptions<T>` (or the short-term recipe); `TransformConfiguration` → `PostConfigure`.
- [ ] Remove `AddAppInitialization()`, `InitAsync()`, `AddPerformanceMeasures()`.
- [ ] Non-generic `ILogger` → `ILogger<T>`.
- [ ] Check `DOTNET_ENVIRONMENT`/`ASPNETCORE_ENVIRONMENT`, `Culture:DefaultCulture` and relative paths under systemd /
  Windows services.

## Logging: CuriosusNLogConfigurator → AddCuriosusNLog

Every app gets the same NLog setup from one call. The old configurator threw a bare `Exception` when NLog.config lacked
one of its variables, including the five mail variables of apps that send no mail, and it needed the `Log` and
`LoggerMail` objects of the root configuration class. `AddCuriosusNLog` reads the `Log` section, sets `outputdir` and
`appname` and leaves everything else to NLog.config.

Removed: `CuriosusNLogConfigurator`, `ILoggingConfigurationOptions` / `LoggingConfigurationOptions` (replaced by
`CuriosusNLogOptions`), `ILoggerMailOptions` / `LoggerMailOptions`, `IConfigurationWithMailLogger`, the mail variables
(`mailto`, `mailfrom`, `smtplogin`, `smtppassword`, `smtpserver`). 

Before:

```yaml
Log:
  LogConfigurationPath: ./NLog.config
  LogOutputDirectory: ./logs
LoggerMail:
  SmtpServer: smtp.example.com
  SmtpPassword: secret
```

```xml
<variable name="smtppassword" value="" />
<target xsi:type="Mail" smtpPassword="${var:smtppassword}" ... />
```

After:

```csharp
var builder = Host.CreateApplicationBuilder(args);
builder.AddCuriosusNLog();
```

```yaml
Log:
  LogConfigurationPath: NLog.config   # relative to the content root
  LogOutputDirectory: logs            # relative to the content root, ${var:outputdir} is the absolute path
```

```xml
<extensions><add assembly="NLog.MailKit" /></extensions>
<target xsi:type="Mail" smtpPassword="${configsetting:item=LoggerMail.SmtpPassword}" ... />
```

Notes:

- `Log:LogConfigurationPath`, `Log:LogOutputDirectory`, `outputdir` and `appname` keep their names. The paths now
  resolve against the content root, not the current directory.
- A value of any section or an environment variable reaches NLog.config with `${configsetting:item=Section.Key}`;
  keep passwords in environment variables or user secrets. Variables that NLog.config doesn't declare are not an error.
- `${aspnet-*}` renderers work without `<add assembly="NLog.Web.AspNetCore"/>`: `CuriosusWebHost.CreateBuilder` of
  Curiosus.Hosting.Web registers them (on a plain `WebApplication.CreateBuilder` pass
  `configureNLogExtensions: e => e.RegisterNLogWeb()`).
- `AddCuriosusNLog` is not part of the host defaults: the app calls it, and an app that later moves to centralized log
  collection removes the call.
- `appStartEmailLog` and `appStopEmailLog` keep their names and messages (`{AppName} is started` / `is stopped`). They
  are written by the host defaults ([#41](https://github.com/curiosus-dev/Curiosus.Utils/issues/41)) whatever the
  logging provider is; with NLog the rules of NLog.config decide where they go. Rules for loggers named after classes:
  `Curiosity.*` → `Curiosus.*`, see the [overview](../index.md#nlog).
- Prefer `throwConfigExceptions="true"` to `throwExceptions="true"`: the second one also rethrows errors of targets at
  runtime.

Checklist:

- [ ] Call `builder.AddCuriosusNLog()` after `AddCuriosusDefaults()`.
- [ ] Move `LoggerMail` settings to any configuration section and read them with `${configsetting}` in NLog.config.
- [ ] Remove the `smtp*` / `mail*` `<variable>` declarations and `<add assembly="NLog.Web.AspNetCore"/>`.
- [ ] Check that relative `Log` paths still point where you expect them to.
