([#79](https://github.com/curiosus-dev/Curiosus.Utils/issues/79)); this page grows with each change of the release.

## Options

The options validated themselves with the options model of `Curiosus.Configuration` (`IValidatableOptions`,
`AssertValid()`), which is deprecated. They are plain classes on `Microsoft.Extensions.Options` now, validated with
data annotations when the host starts, and the `IPostgresRequestProcessorNodeOptions` interface is replaced with the
`PostgresRequestProcessorNodeOptions` class.

| Before | Now |
|---|---|
| `IPostgresRequestProcessorNodeOptions` implemented by your `RequestProcessorNodeOptions` subclass | derive from `PostgresRequestProcessorNodeOptions` |
| `AddPostgresRequestProcessor<...>(nodeOptions)` with an instance | `AddPostgresRequestProcessor<...>()` binds the `RequestProcessor` section; pass another section path as the first argument, an `Action<TOptions>` as the second |
| `AssertValid()` in `AddPostgresRequestProcessor`, the bootstrapper and `DbEventReceiver` constructors | `OptionsValidationException` when the host starts; `DbEventReceiver` checks only for `null` |
| `PostgresEventReceiverOptions.Validate(prefix)` | `[Range]` on `KeepAliveSec` and `ReconnectionPauseMs`, `[PgChannelNames]` on `EventNames` |

`PgChannelNamesAttribute` is public: put it on a channel list of your own options to get the same rules.

Before:

```csharp
public class MyNodeOptions : RequestProcessorNodeOptions, IPostgresRequestProcessorNodeOptions
{
    public PostgresEventReceiverOptions PostgresEventReceiver { get; } = new();

    public string ConnectionString { get; set; } = null!;

    public override IReadOnlyCollection<ConfigurationValidationError> Validate(string? prefix = null)
    {
        var errors = new ConfigurationValidationErrorCollection(prefix);
        errors.AddErrors(base.Validate(prefix));
        errors.AddErrorIf(String.IsNullOrWhiteSpace(ConnectionString), nameof(ConnectionString), "can't be empty");
        errors.AddErrors(PostgresEventReceiver.Validate(nameof(PostgresEventReceiver)));
        return errors;
    }
}

configuration.AssertValid();
services.AddPostgresRequestProcessor<
    MyRequest, MyWorker, WorkerBasicExtraParams, MyBootstrapper, MyNodeOptions, MyDispatcher, MyProcessingInfo>(
    configuration.RequestProcessor);
```

After:

```csharp
public class MyNodeOptions : PostgresRequestProcessorNodeOptions
{
    [Required]
    public string ConnectionString { get; set; } = null!;
}

services.AddPostgresRequestProcessor<
    MyRequest, MyWorker, WorkerBasicExtraParams, MyBootstrapper, MyNodeOptions, MyDispatcher, MyProcessingInfo>();
```

`PostgresEventReceiver` is validated with the node options (`[ValidateObjectMembers]`). Rules over several properties
of your subclass go to your own `IValidateOptions<MyNodeOptions>`, and the options of a subclass of a subclass are
validated as described on the
[Curiosus.RequestProcessing 3.0](../curiosus-requestprocessing/3.0.md#subclasses-of-the-options) page.

Checklist:

- [ ] Derive the node options from `PostgresRequestProcessorNodeOptions` and remove
  `IPostgresRequestProcessorNodeOptions` and the `PostgresEventReceiver` property you declared.
- [ ] Replace `AddPostgresRequestProcessor<...>(instance)` with `AddPostgresRequestProcessor<...>()` (or pass the section
  path when the options are not in `RequestProcessor`), remove `AssertValid()` calls.
- [ ] Move the `Validate(prefix)` override to attributes and an `IValidateOptions<T>`.
- [ ] Bootstrappers: change the constraint `RequestProcessorNodeOptions, IPostgresRequestProcessorNodeOptions` to
  `PostgresRequestProcessorNodeOptions` if you repeat it in your own generic types.

## Channel names are case-sensitive

`LISTEN` was built by inserting each name of `PostgresEventReceiverOptions.EventNames` into SQL as is. A name like
`x; DROP TABLE requests` ran SQL with the listener's credentials, and PostgreSQL folded mixed-case names to lower case.
Now every name is quoted as an identifier and used exactly as written.

| `EventNames` | Sent with | 2.0 | 3.0 |
|---|---|---|---|
| `new_request` | any | received | received |
| `NewRequest` | `NOTIFY NewRequest` (unquoted, folded to `newrequest`) | received | **not received** |
| `NewRequest` | `pg_notify('NewRequest', ...)`, `NOTIFY "NewRequest"`, `NotifyAsync("NewRequest")` | **not received** | received |

Checklist:

- [ ] For every name in `EventNames` with upper-case letters: either change it to lower case, or make every sender use
  the same case with `pg_notify`, a quoted `NOTIFY "Name"` or `NotifyAsync`. Check triggers and functions in the
  database too.

## Invalid channel names fail at startup

A channel name must be non-empty, at most 63 bytes in UTF-8 (longer names were truncated by PostgreSQL) and contain no
NUL character. Options validation now fails at startup with the index of the bad name
(`EventNames:1` of `PostgresEventReceiver`); an empty name was skipped with a warning before.

Checklist:

- [ ] Remove empty entries from `EventNames` (for example a trailing empty item in YAML or an unset environment
  variable).

## Send notifications with NotifyAsync

Building `NOTIFY` SQL by string interpolation has the same injection and case-folding problems as `LISTEN` had. The
new `NotifyAsync` extension methods run `pg_notify` with parameters and validate the channel name.

Before:

```csharp
await using var command = new NpgsqlCommand($"NOTIFY {ChannelName};", connection);
await command.ExecuteNonQueryAsync(ct);
```

After, in the transaction that inserts the request, so the notification goes out only after the commit:

```csharp
await using var transaction = await connection.BeginTransactionAsync(ct);
// INSERT INTO requests ...
await connection.NotifyAsync(ChannelName, cancellationToken: ct);
await transaction.CommitAsync(ct);
```

Outside a transaction, `await dataSource.NotifyAsync(ChannelName, payload, ct)` uses a connection of an
`NpgsqlDataSource`. The payload must be shorter than 8000 bytes.

Checklist:

- [ ] Replace `NOTIFY` built with interpolation or concatenation in C# with `NotifyAsync`.
- [ ] Send it in the transaction that inserts the request, not after it.

## Connection strings are no longer in exception messages

`MonitoredDatabase.ToString()` returned the connection string with its password, and it reached exception messages
(a database added twice, a database that is not listened to) and logs. It returns `Host:Port/Database` now; equality
still compares the full connection string.

Checklist:

- [ ] Rotate database passwords that reached logs through these messages.
- [ ] Code that used `MonitoredDatabase.ToString()` to get the connection string: use `ConnectionString`.
