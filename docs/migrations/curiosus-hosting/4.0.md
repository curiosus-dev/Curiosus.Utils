Requires `net9.0` or `net10.0`. Coming from `Curiosity.*` 1.x? Start with the [overview](../index.md).

`Curiosus.Hosting` 4.0 replaces the bootstrappers with extension methods on `IHostApplicationBuilder`. This page grows
with each change of the release ([#41](https://github.com/curiosus-dev/Curiosus.Utils/issues/41),
[#43](https://github.com/curiosus-dev/Curiosus.Utils/issues/43)–[#46](https://github.com/curiosus-dev/Curiosus.Utils/issues/46)).

## Breaking changes

- [Logging: CuriosusNLogConfigurator → AddCuriosusLogging](#logging-curiosusnlogconfigurator--addcuriosuslogging)
  ([#43](https://github.com/curiosus-dev/Curiosus.Utils/issues/43))

## Logging: CuriosusNLogConfigurator → AddCuriosusLogging

Every app gets the same NLog setup from one call. The old configurator threw a bare `Exception` when NLog.config lacked
one of its variables, including the five mail variables of apps that send no mail, and it needed the `Log` and
`LoggerMail` objects of the root configuration class. `AddCuriosusLogging` reads the `Log` section, sets `outputdir` and
`appname` and leaves everything else to NLog.config.

Removed: `CuriosusNLogConfigurator`, `ILoggingConfigurationOptions` / `LoggingConfigurationOptions` (replaced by
`CuriosusLoggingOptions`), `ILoggerMailOptions` / `LoggerMailOptions`, `IConfigurationWithMailLogger`, the mail variables
(`mailto`, `mailfrom`, `smtplogin`, `smtppassword`, `smtpserver`). `Curiosus.Hosting` and `Curiosus.Hosting.Web` no
longer reference `MailKit` and `NLog.MailKit`. The bootstrappers keep working until they are replaced: they load NLog the
new way, so the points below apply to them too, except that their relative paths still resolve against the current
directory.

Before:

```yaml
Log:
  LogConfigurationPath: ./NLog.config
  LogOutputDirectory: ./logs
LoggerMail:
  SmtpServer: smtp.example.com
  SmtpPassword: secret
```

```xml
<variable name="smtppassword" value="" />
<target xsi:type="Mail" smtpPassword="${var:smtppassword}" ... />
```

After:

```csharp
var builder = Host.CreateApplicationBuilder(args);
builder.AddCuriosusLogging();                       // WebApplicationBuilder: also registers ${aspnet-*}
```

```yaml
Log:
  LogConfigurationPath: NLog.config   # relative to the content root
  LogOutputDirectory: logs            # relative to the content root, ${var:outputdir} is the absolute path
```

```xml
<extensions><add assembly="NLog.MailKit" /></extensions>
<target xsi:type="Mail" smtpPassword="${configsetting:item=LoggerMail.SmtpPassword}" ... />
```

Notes:

- `Log:LogConfigurationPath`, `Log:LogOutputDirectory`, `outputdir` and `appname` keep their names. The paths now
  resolve against the content root, not the current directory.
- A value of any section or an environment variable reaches NLog.config with `${configsetting:item=Section.Key}`;
  keep passwords in environment variables or user secrets. Variables that NLog.config doesn't declare are not an error.
- **Pitfall:** `<add assembly="NLog.MailKit"/>` without a package reference together with `throwExceptions="true"`
  makes the app fail on startup: add the `NLog.MailKit` package to the app.
- `${aspnet-*}` renderers work on a `WebApplicationBuilder` without `<add assembly="NLog.Web.AspNetCore"/>`.
- `appStartEmailLog` and `appStopEmailLog` keep their names and messages (`{AppName} is started` / `is stopped`); the
  rules of NLog.config decide where they go. Rules for loggers named after classes: `Curiosity.*` → `Curiosus.*`,
  see the [overview](../index.md#nlog).
- Prefer `throwConfigExceptions="true"` to `throwExceptions="true"`: the second one also rethrows errors of targets at
  runtime.

Checklist:

- [ ] Replace the bootstrapper call with `builder.AddCuriosusLogging()` (once the bootstrappers are gone).
- [ ] Move `LoggerMail` settings to any configuration section and read them with `${configsetting}` in NLog.config.
- [ ] Add the `NLog.MailKit` package if NLog.config has a MailKit mail target.
- [ ] Remove the `smtp*` / `mail*` `<variable>` declarations and `<add assembly="NLog.Web.AspNetCore"/>`.
- [ ] Check that relative `Log` paths still point where you expect them to.
