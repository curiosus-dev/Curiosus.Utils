Requires `net9.0` or `net10.0`. Coming from `Curiosity.*` 1.x? Start with the [overview](../index.md).

`Curiosus.Configuration` 3.0 moves options to `Microsoft.Extensions.Options`
([#44](https://github.com/curiosus-dev/Curiosus.Utils/issues/44)). The package keeps two helpers on top of it,
`AddCuriosusOptions<T>` and `LogConfigurationOnStart`, and removes its own options model: `IValidatableOptions`,
`AssertValid`, `ConfigurationValidationError(Collection)`, `ConfigurationValidationException`, `ILoggableOptions`,
`ConfigurationPrinter`, `IConfigurationProvider<T>` and `ConfigurationProviderBase<T>`.

- **Your own options can move now**: the helpers are in `Curiosus.Configuration` since 2.1, next to the old types.
- **Options of Curiosus packages** move with the next major of each package, see its migration page in the
  [package table](../index.md#packages). Libraries don't need the helpers: they use `AddOptions<T>()` with
  `ValidateOnStart()` directly and don't depend on this package.

## Why

- Options were POCO singletons: a snapshot, no reload, separate from `IConfiguration`.
- `AssertValid()` ran in constructors, so invalid options failed on first resolve, not at start.
- `AddXxx(optionsInstance)` ruled out `ValidateOnStart`, `IOptionsMonitor` and named options.
- `ConfigurationPrinter` printed the whole options object; the startup dump now prints listed sections from
  `IConfiguration`, with the source of each value.

## Options classes

Before:

```csharp
public class SmtpOptions : ILoggableOptions, IValidatableOptions
{
    public string Host { get; set; } = null!;
    public int Port { get; set; } = 25;
    public TlsOptions Tls { get; set; } = new();

    public IReadOnlyCollection<ConfigurationValidationError> Validate(string? prefix = null)
    {
        var errors = new ConfigurationValidationErrorCollection(prefix);
        errors.AddErrorIf(String.IsNullOrWhiteSpace(Host), nameof(Host), "can't be empty");
        errors.AddErrorIf(Port <= 0, nameof(Port), "must be positive");
        errors.AddErrors(Tls.Validate($"{prefix}:{nameof(Tls)}"));
        return errors;
    }
}

var options = configuration.GetSection("Smtp").Get<SmtpOptions>()!;
options.AssertValid("Smtp");
services.AddSingleton(options);
```

After:

```csharp
public class SmtpOptions
{
    [Required]
    public string Host { get; set; } = null!;

    [Range(1, 65535)]
    public int Port { get; set; } = 25;

    [ValidateObjectMembers]
    public TlsOptions Tls { get; set; } = new();
}

services.AddCuriosusOptions<SmtpOptions>("Smtp");   // bind + data annotations + ValidateOnStart

public class MailSender(IOptions<SmtpOptions> options) { /* options.Value */ }
```

- Rules become attributes (`[Required]`, `[Range]`, `[Url]`, `[RegularExpression]`, ...). Nested objects and collections
  get `[ValidateObjectMembers]` and `[ValidateEnumeratedItems]`: the paths in errors are built for you.
- Rules across several fields: `IValidatableObject` on the class, or an `IValidateOptions<T>` registered with
  `services.AddSingleton<IValidateOptions<SmtpOptions>, SmtpOptionsValidator>()`, or `.Validate(o => ..., "message")` on
  the builder that `AddCuriosusOptions` returns.
- Several instances of one options class: named options, `AddCuriosusOptions<SmtpOptions>("primary", "Mail:Primary")`
  and `IOptionsMonitor<SmtpOptions>.Get("primary")`.
- `PostConfigure<T>` replaces code that computed derived values after loading: it runs before validation.

## Injecting options through an interface

Before, options were registered as an app interface they implemented. Keep the interface if many classes use it:

```csharp
services.AddCuriosusOptions<AppOptions>("App");
services.AddSingleton<IAppOptions>(sp => sp.GetRequiredService<IOptions<AppOptions>>().Value);
```

## Validation errors

`ConfigurationValidationException` on the first resolve becomes `OptionsValidationException` when the host starts.
Its `Message` joins all failures, for example
`DataAnnotation validation failed for 'SmtpOptions.Tls' members: 'Port' with the error: '...'`.

## Printing the configuration at startup

Before, `ILoggableOptions` marked options that `ConfigurationPrinter` printed. After:

```csharp
services.LogConfigurationOnStart();                       // the whole configuration
services.LogConfigurationOnStart("Smtp", "Processors");   // or only these sections
services.LogConfigurationOnStart(o => o.ExcludedSections.Add("Serilog"));
```

Each value is printed on its own line with the provider it came from (file, environment variables, command line), so
you see which source won. Without sections the whole configuration is printed, except environment variables without a
section that no other provider sets (`PATH`, `HOSTNAME`, ...); `Smtp__Password` is printed as `Smtp:Password`, masked.
Secrets are masked by the same rules as before (#39), plus values with URI credentials anywhere; connection strings
keep only well-known non-secret keys. The `[Secret]`/`[NotSecret]` attributes have no counterpart, because the dump
reads `IConfiguration`, not option classes: rename a secret with an unusual name or exclude its section.

## Checklist

- [ ] Remove `ILoggableOptions` and `IValidatableOptions` from your options classes; move `Validate` rules to
  attributes or an `IValidateOptions<T>`.
- [ ] Replace `Get<T>()` + `AssertValid()` + `AddSingleton(options)` with `AddCuriosusOptions<T>("Section")`, and inject
  `IOptions<T>` (or keep an interface registration, see above).
- [ ] Replace nested `Validate($"{prefix}:Child")` calls with `[ValidateObjectMembers]` / `[ValidateEnumeratedItems]`.
- [ ] Replace the `ConfigurationPrinter` dump with `LogConfigurationOnStart()` (or listed sections).
- [ ] Catch or log `OptionsValidationException` instead of `ConfigurationValidationException`.
- [ ] Options of Curiosus packages: follow the migration page of each package's next major.
