## HtmlSanitizerHelper → IHtmlSanitizer

`HtmlSanitizerHelper.Sanitize` decoded the sanitizer output with `WebUtility.HtmlDecode`. The sanitizer keeps
markup-looking text as entities, so `<p>&lt;script&gt;alert(document.cookie)&lt;/script&gt;</p>` passed it unchanged and the
decode turned it into a live `<script>` that `Html.Raw` executed (stored XSS). The allow-list also contained `id` and
`class`: user content could define `<a id="config">` to shadow the page's global variables (DOM clobbering) and reuse
the app's CSS classes for fake overlays and buttons.

Before:

```csharp
entity.Description = HtmlSanitizerHelper.Sanitize(input.Description);
```

After:

```csharp
builder.Services.AddCuriosusHtmlSanitizer();   // or (o => o.AllowedAttributes.Add("class"))

public class ArticleService(IHtmlSanitizer sanitizer)
{
    public void Save(Article entity, ArticleInput input) =>
        entity.Description = sanitizer.Sanitize(input.Description);
}
```

- The output keeps entities encoded (`&amp;`, `&lt;`, `&nbsp;`): that is correct HTML for `Html.Raw` and displays the
  same. Don't decode it.
- `id` and `class` are stripped unless `configure` adds them back. The rest of the allow-list is unchanged:
  `audio`/`video`/`source` with `controls`, `preload`, `autoplay`, `muted`, `loop`; `face`; `mailto:`, `sip:`, `tel:`,
  `skype:` links.
- `IHtmlSanitizer` is the interface of the Ganss.Xss package (`HtmlSanitizer`), registered as a singleton: it is
  thread-safe once configured.

Checklist:

- [ ] Replace `HtmlSanitizerHelper.Sanitize` with an injected `IHtmlSanitizer` after `AddCuriosusHtmlSanitizer()`.
- [ ] **Re-sanitize content stored through the old helper** (a one-off job over the stored HTML), or sanitize on output
  until it is done: it may already contain live scripts.
- [ ] Add `class` (or `id`) in `configure` only if the content needs it and the page's CSS and scripts don't depend on
  user-controllable class names or ids.

## MVCBaseController: redirects and error pages

Several holes of `MVCBaseController` are closed:

| Before | Now |
|---|---|
| `RedirectInternal(returnUrl)` redirected to any URL: `/account/login?returnUrl=//evil.example` sent the user to an attacker site after a real login | local URLs (`Url.IsLocalUrl`: `/orders/5`, `~/orders`) and `http(s)` URLs to hosts of `RedirectAllowListOptions`; anything else (`https://evil…`, `//…`, `/\…`, `javascript:`, empty) goes to Home/Index |
| `AjaxError.cshtml` rendered the text with `Html.Raw` | encoded: HTML in the text shows as text |
| the ajax error answer and the page of a bad request showed `ex.Message` (SQL, paths, hosts, user input) | the app's `errorText` or the generic localized message; the exception is only logged |
| `/home/errorview?errorText=…` showed any text on the app's error page | the routable endpoint binds nothing from the request |
| every public helper was an action on every derived controller: `ErrorViewWithCode`, `ErrorViewParams` (formats an attacker-supplied `fmt`), `AjaxGridErrorResponse` ×3, `AjaxError` ×2, `AjaxSuccess` | `[NonAction]` helpers; the only inherited action is the error endpoint |

The error endpoint keeps its route: `UseExceptionHandler("/home/ErrorView")` (or `UseCuriosusExceptionHandler`) still
works. It is `HandleError()` with `[ActionName("ErrorView")]`, `[AllowAnonymous]` and `[IgnoreAntiforgeryToken]`, with no
HTTP method attribute, because the exception handler re-executes POST requests as well. Calls from app code are
unchanged: `return ErrorView("Order not found");` is the helper now. The exception is logged under the controller's
category: unhandled → Error, bad request → Warning, cancellation → Information.

External sites the app sends users back to (its public domains, the front-end address) go to an allow-list; any
other external URL goes to Home/Index:

```csharp
builder.Services.Configure<RedirectAllowListOptions>(o =>
{
    o.AllowedHosts.Add("www.example.com");   // public domain
    o.AllowedHosts.Add("app.example.com");   // front-end
});
// or bind a section: builder.Services.Configure<RedirectAllowListOptions>(builder.Configuration.GetSection("Redirects"))
```

Hosts are compared exactly and case-insensitively (`evil.app.example.com` is not `app.example.com`); only `http` and
`https` URLs without user info are allowed, URLs with a backslash, whitespace or control characters are rejected, and
the redirect goes to the canonical form of the validated URL.

Checklist:

- [ ] Add the public domains and the front-end host to `RedirectAllowListOptions` if `returnUrl` may point there.
- [ ] Links or forms pointing to `ErrorViewWithCode`, `ErrorViewParams`, `AjaxGridErrorResponse`, `AjaxError`,
  `AjaxSuccess` → an action of your own controller that calls the helper.
- [ ] Ajax error texts that relied on HTML markup are shown as text now.
- [ ] Logging rules: the error endpoint logs under the controller's category.

## DataProtection

`AddCuriosusDataProtection(options)` with `IsEnabled: false` (and `DisableDataProtection()`) swapped the registered
`IDataProtectionProvider` for a stub that returned data unprotected: `Protect(x) => x`. It did so only when
`AddDataProtection()` had been registered before the call (directly or by `AddAuthentication`, antiforgery, Identity),
so the same configuration was safe or not depending on the order of lines. With the stub an auth cookie is plain
Base64Url: a user decodes it, changes their role or id and signs in as someone else. The stub is gone; the method always
adds data protection and only configures it.

Before:

```csharp
services.AddCuriosusDataProtection(configuration.DataProtection);   // DataProtectionOptions with IsEnabled
```

After:

```csharp
builder.Services.AddCuriosusDataProtection()   // section "DataProtection"; or AddCuriosusDataProtection("Web:DataProtection")
    .ProtectKeysWithCertificate(certificate);   // optional: the result is the IDataProtectionBuilder
```

| `DataProtection` section before | After |
|---|---|
| `IsEnabled: true`, `ApplicationName`, `KeyRingPath` | keep both values **exactly**; add `DisableAutomaticKeyGeneration: true` to keep the old behaviour (the operator creates and rotates keys) or leave it out to let the framework rotate them |
| `IsEnabled: false` or no `IsEnabled` | delete the section, or keep `ApplicationName`/`KeyRingPath` without `IsEnabled`: data is protected either way |
| no section | unchanged: framework defaults |

- **Keep `ApplicationName` byte for byte.** It is the discriminator of every purpose chain: a different value, even in
  case, invalidates all auth cookies, antiforgery tokens and Identity tokens, including password-reset and e-mail
  confirmation links already sent. Keep the same key ring as well.
- `KeyRingPath` must exist and `DisableAutomaticKeyGeneration` needs it: otherwise the host doesn't start
  (`OptionsValidationException`). A missing directory is an error, not a fallback to the default location; without
  `KeyRingPath` the framework default is used (a user profile folder, or in-memory keys lost on restart where there
  is none, such as a container). With generation disabled and an empty key ring, the first `Protect` fails.
- Environments that ran the stub (typically development with a section without `IsEnabled`): the cookies they issued
  can't be read any more, users sign in once again.
- Several instances share the key ring: the same directory, or another repository through the returned builder.
- The startup warnings about ephemeral or unencrypted keys stay: they mean keys are lost on restart or stored in clear.
- The same setup without the library:
  `services.AddDataProtection().SetApplicationName(name).PersistKeysToFileSystem(new DirectoryInfo(path)).DisableAutomaticKeyGeneration();`

Checklist:

- [ ] Call `AddCuriosusDataProtection()` (or pass the path of your section).
- [ ] Remove `IsEnabled` and calls of `DisableDataProtection()`.
- [ ] Keep `ApplicationName` and the key ring exactly; decide on `DisableAutomaticKeyGeneration`.
- [ ] Expect one sign-in round for users of environments that ran unprotected.

## MVCBaseController error actions without a logger

The error actions `ErrorView`, `ErrorViewWithCode` and `ErrorViewParams` took a `[FromServices] ILogger`: the
non-generic logger named `main` that the Curiosus.Hosting bootstrappers registered. Curiosus.Hosting 4.0 doesn't, so the
actions failed to resolve. They now create their logger from `ILoggerFactory` with the actual controller as the category
(`MyApp.Controllers.HomeController`) instead of `main`.

Before:

```csharp
public IActionResult Save(Model model, [FromServices] ILogger logger)
{
    if (!ModelState.IsValid) return ErrorView(logger, "Invalid data");
    // ...
}
```

After:

```csharp
public IActionResult Save(Model model)
{
    if (!ModelState.IsValid) return ErrorView("Invalid data");
    // ...
}
```

Checklist:

- [ ] Drop the logger argument from calls to `ErrorView`, `ErrorViewWithCode`, `ErrorViewParams`.
- [ ] Controllers log through their own `ILogger<TController>`, not a non-generic `ILogger`.
- [ ] NLog rules on the `main` logger for these errors → the controller's namespace.
