## MVCBaseController: redirects and error pages

Several holes of `MVCBaseController` are closed:

| Before | Now |
|---|---|
| `RedirectInternal(returnUrl)` redirected to any URL: `/account/login?returnUrl=//evil.example` sent the user to an attacker site after a real login | only local URLs (`Url.IsLocalUrl`: `/orders/5`, `~/orders`); `https://…`, `//…`, `/\…`, `javascript:` and empty go to Home/Index |
| `AjaxError.cshtml` rendered the text with `Html.Raw` | encoded: HTML in the text shows as text |
| the ajax error answer and the page of a bad request showed `ex.Message` (SQL, paths, hosts, user input) | the app's `errorText` or the generic localized message; the exception is only logged |
| `/home/errorview?errorText=…` showed any text on the app's error page | the routable endpoint binds nothing from the request |
| every public helper was an action on every derived controller: `ErrorViewWithCode`, `ErrorViewParams` (formats an attacker-supplied `fmt`), `AjaxGridErrorResponse` ×3, `AjaxError` ×2, `AjaxSuccess` | `[NonAction]` helpers; the only inherited action is the error endpoint |

The error endpoint keeps its route: `UseExceptionHandler("/home/ErrorView")` (or `UseCuriosusExceptionHandler`) still
works. It is `HandleError()` with `[ActionName("ErrorView")]`, `[AllowAnonymous]` and `[IgnoreAntiforgeryToken]`, with no
HTTP method attribute, because the exception handler re-executes POST requests as well. Calls from app code are
unchanged: `return ErrorView("Order not found");` is the helper now. The exception is logged under the controller's
category: unhandled → Error, bad request → Warning, cancellation → Information.

A redirect to an external site after a form is now explicit:

```csharp
private static readonly HashSet<string> AllowedHosts = ["pay.example.com"];

public IActionResult Done(string returnUrl) =>
    Uri.TryCreate(returnUrl, UriKind.Absolute, out var uri) && AllowedHosts.Contains(uri.Host)
        ? Redirect(returnUrl)
        : RedirectInternal(returnUrl);
```

Checklist:

- [ ] Find `RedirectInternal` calls that are meant to leave the site and make them explicit with an allow-list.
- [ ] Links or forms pointing to `ErrorViewWithCode`, `ErrorViewParams`, `AjaxGridErrorResponse`, `AjaxError`,
  `AjaxSuccess` → an action of your own controller that calls the helper.
- [ ] Ajax error texts that relied on HTML markup are shown as text now.
- [ ] Logging rules: the error endpoint logs under the controller's category.

## MVCBaseController error actions without a logger

The error actions `ErrorView`, `ErrorViewWithCode` and `ErrorViewParams` took a `[FromServices] ILogger`: the
non-generic logger named `main` that the Curiosus.Hosting bootstrappers registered. Curiosus.Hosting 4.0 doesn't, so the
actions failed to resolve. They now create their logger from `ILoggerFactory` with the actual controller as the category
(`MyApp.Controllers.HomeController`) instead of `main`.

Before:

```csharp
public IActionResult Save(Model model, [FromServices] ILogger logger)
{
    if (!ModelState.IsValid) return ErrorView(logger, "Invalid data");
    // ...
}
```

After:

```csharp
public IActionResult Save(Model model)
{
    if (!ModelState.IsValid) return ErrorView("Invalid data");
    // ...
}
```

Checklist:

- [ ] Drop the logger argument from calls to `ErrorView`, `ErrorViewWithCode`, `ErrorViewParams`.
- [ ] Controllers log through their own `ILogger<TController>`, not a non-generic `ILogger`.
- [ ] NLog rules on the `main` logger for these errors → the controller's namespace.
