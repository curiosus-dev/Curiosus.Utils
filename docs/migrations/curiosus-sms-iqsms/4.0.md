Requires `net9.0` or `net10.0`. Coming from `Curiosity.*` 1.x? Start with the [overview](../index.md).

4.0 registers `IqsmsOptions` with `Microsoft.Extensions.Options`: `AddIqsmsSender` binds them from the `Iqsms`
configuration section and validates them when the host starts, like the options of ASP.NET Core and other libraries.

## Breaking changes

- [Options](#options) ([#44](https://github.com/curiosus-dev/Curiosus.Utils/issues/44))

Also in this release: the sender posts JSON with the login and the password in the body instead of the URL query.
**Rotate the iqsms password** if logs of proxies, gateways or the provider were kept, see the
[CHANGELOG](https://github.com/curiosus-dev/Curiosus.Utils/blob/main/src/SMS/Curiosus.SMS.Iqsms/CHANGELOG.md)
([#84](https://github.com/curiosus-dev/Curiosus.Utils/issues/84)).

## Options

`IqsmsOptions` implemented the validation model of `Curiosus.Configuration` (`IValidatableOptions`, `AssertValid()`),
which is going away. Now the rules are data annotations (`[Required]` on `Login` and `Password`), checked by
`ValidateOnStart`: invalid configuration stops the host with `OptionsValidationException` naming the option, instead of
an exception from `AddIqsmsSender`. A login or password of only whitespace is rejected too.

Before:

```csharp
var iqsmsOptions = configuration.GetSection("IqsmsOptions").Get<IqsmsOptions>()!;
services.AddIqsmsSender(iqsmsOptions);
```

After:

```csharp
services.AddIqsmsSender();   // binds the "Iqsms" section (IqsmsOptions.SectionName)

// your configuration has another section: pass it, the files stay as they are
services.AddIqsmsSender("IqsmsOptions");

// values set in code are applied after the section and override it; without a section they are enough
services.AddIqsmsSender(configure: options =>
{
    options.Login = "my-login";
    options.Password = "my-password";
});
```

`useAsDefaultSender` stays, after the section and `configure`: `services.AddIqsmsSender(useAsDefaultSender: false)`.
Only the first call of `AddIqsmsSender` binds its section and registers the validation; later calls add their
`configure` only.

`AddIqsmsSender` reads `IConfiguration` from the service provider, which every host registers. A bare
`ServiceCollection` (in tests, for example) needs one: `services.AddSingleton<IConfiguration>(configuration)`.

Code that creates the sender itself passes `IOptions<IqsmsOptions>`:

```csharp
var sender = new IqsmsSender(logger, Options.Create(iqsmsOptions), httpClientFactory);
```

`Options.Create` doesn't validate: the sender no longer checks the options in its constructor.

A subclass of `IqsmsOptions` keeps working as a plain class: drop its `Validate(prefix)` override and move the rules to
attributes or an `IValidateOptions<IqsmsOptions>` registered next to `AddIqsmsSender`:

```csharp
services.AddIqsmsSender();
services.AddSingleton<IValidateOptions<IqsmsOptions>, MyIqsmsOptionsValidator>();
```

Checklist:

- [ ] Replace `GetSection(...).Get<IqsmsOptions>()` and `AddIqsmsSender(options)` with `AddIqsmsSender()`, passing your
  section name if it isn't `Iqsms`, or with `AddIqsmsSender(configure: o => ...)`.
- [ ] Move named arguments: `useAsDefaultSender` now comes after `configSectionPath` and `configure`.
- [ ] Remove `AssertValid()` calls and `IValidatableOptions`/`ILoggableOptions` from your code around `IqsmsOptions`.
- [ ] Wrap options passed to `new IqsmsSender(...)` in `Options.Create(...)`.
- [ ] Start the app once with an empty password and check that it stops with an `OptionsValidationException`.
